服务已从仓库根重启（`node apps/web/dist/index.js`，8787，ROOT/API 双 200），dist/prompt.js 已确认只剩

**采纳建议，但在关键一处刻意不同**：建议里隐含「让 AI 输出结构化 JSON」，本项目**不改**——

**消息 parts 模型**（最关键的一个决定）：`MessagePart = text | activity | artifact`，

## Phase AE：基线池收到前 10

**用户要求**：「榜首的实况统计前 10 即可，读取数据也是前 10 即可，100 太多了」。

**实测结论**：WCL `characterRankings` **没有行数参数**——`limit` 不在字段参数表里
（会报 unknown argument），每页固定返回 100 条；`count` / `hasMorePages` 描述的是
**分页**而非总体量（page 1 和 page 2 都回 `count=100`）。所以「取前 10」只能是
**客户端截断**，网络字节不会减少——这点要如实知道，别以为省了带宽。

**改了什么**
- `@wcl/application`：`REFERENCE_POOL_SIZE = 10`；`getEncounterRankings` 增 `limit` 参数
  （client.ts 内 slice）；`count` 仍是 WCL 那一页的原始行数，与「实际用了几条」**刻意分开**
  ——这正是「前 100 名」不再泄漏进文案的原因。pool 文案改「前 10 名」，`reference.top` 就是整池。
- UI：`MAX_ARTIFACT_TOP_RUNS = 10`；`ReferenceCard` 改成**榜首实况列表**
  （序号/名字/层级/DPS/日志直链），前 3 条内联、其余「展开剩余 N 条」。
- **brief 仍只给模型 3 条**（模型只要够引用，不需浏览列表）——这个不对称是**有意的**，
  已写进 `docs/ui-architecture.md` §6，别去「对齐」它。
- 两份提示词都补：池是小样本 = **上限参照**，禁止「超过 X% 玩家 / 分位」人群措辞。

**踩到的真陷阱（值得记）**：改完 pool 大小后 live 复验**仍然显示「前 100 名」**——
因为走了 SQLite 分析缓存，而缓存 key 只含 `ANALYZER_VERSION`，池大小变更不会自动失效。
→ 凡是「改变所有战斗语义」的改动（口径、池、阈值），**必须 bump ANALYZER_VERSION**。
本次 0.10.0 → 0.11.0（package.json 同步），缓存失效后复验才拿到「前 10 名 / 池 +20~+21」。

**语义变化（如实记录）**：同一场（诸王之眠 +10 元素萨）差距由 **-50.4% → -54.2%**、
池层级由 **+19~+21 → +20~+21**（顶尖 10 条的中位更高、样本更靠顶）。
已写进 `ui-architecture.md` §7：池大小变化会改动所有战斗数值 + 必须 bump 版本。

**live 复验**：artifact 带 10 条榜首实况，**10 条全部有 permalink**（榜首 小奈电下 +21 296158）。
测试 net +6（wcl-client 3 / application 2 / web artifact 1 / web-ui 榜首列表+展开 1）；
全仓 487 用例 + lint 全绿，服务新 dist 重启（8787 双 200）。

## Phase AF：榜首逐场对标（「我具体差在哪」）

**起因**：用户「我想让 ai 帮我分析同副本的榜首的数据，然后横向对比一下我具体差在哪，
这个功能目前无法实现吗」。答案是**能**——但此前确实不能：只有聚合基线（分位 + 10 条 permalink），
回答「离顶尖有多远」，回答不了「差在哪」。

**先做可行性实测再写代码**（这一步是关键）：
① 榜单条目带 `report.code` / `report.fightID` → 能定位到那一场；
② 对方报告是公开的 → `getPlayers` 能按名字匹配到 actor；
③ 同一套 analyzer 能直接跑对方那一场（真实日志：对方 1471 次施法 / 6033 个 buff 全部拉到）。

**用户后来给了具体样本**：我的 `fXdMjWKJbpna6yHv?fight=13`（黑脸法/奥法 +10）对照
`DykTVdzMJwhvBKm2?fight=28`（Qingxingood/奥法 +21）。**自动基线精确命中了他说的那一场
（榜首 #1 = Qingxingood，report 正是 DykTVdzMJwhvBKm2）**——这既是验证也说明榜单链路是对的。

**新增能力**：`packages/application/src/reference-compare.ts`（纯函数）+ `AppService.compareToTopRun()`。
只比**速率**（施法/分钟、GCD/分钟、未施法占比、每技能次/分钟），因为两场时长不同、绝对次数不可比；
DPS 照给但**强制带 note**（层数/装等/路线未剥离）；finding 按规则 id 求差；
**判定档分布只在两边 scenario 相同时才算 comparable**。

**真实结果（奥法那对）**：施法 37.0 vs 43.1 次/分（-14.2%）、未施法占比 72.6% vs 62.7%、
DPS 差 -40.9%（带层数 note）、每个核心技能都低 11~27% → 「整体施法频率偏低 + 空转偏多」。
判定档 `comparable=false`（我 st / 他 aoe）——**如实标注不可横比**，不硬画对比。

**技能名的真解法（省下一次踩坑）**：事件里只有 `abilityId`（WCL 的 casts JSON 没有嵌套 ability
对象，所以归一化后 `abilityName` 恒空）。`gameData.abilities(ids:[...])` **不存在**
（实测 `Unknown argument "ids"`）；正解是 `report.masterData.abilities { gameID name }`——
**一次请求拿整份报告的技能表，cn 站直接给官方中文名**（新 `WclClient.getAbilityNames`）。
过滤 `gameID: 0`（WCL 的 "Unknown Ability" 占位符）。

**必须 bump 版本**：`RankingReference.top[]` 加了 `reportCode`/`fightId`，而缓存里的旧结果没有
→ `ANALYZER_VERSION` 0.11.0 → 0.12.0（package.json 同步）。**同一条规则第二次生效**：
凡是改变结果形状/语义的改动，不 bump 就会在缓存上静默失败。

**用户当场抓到一处真 UX 问题（值得记）**：榜首日志的链接我原本放在卡片**最底部**，
用户按「右上角应该有」去找，反馈「这个链接我好像没拿到」。核实：链接确实渲染了（全局 `a` 给了青色），
但长卡片底部的链接**等于不可见**。→ 移到 `.compare-head` 右上（紧邻对手名字），
并把「两者层数不同」这类**关键前提从 tooltip 改成可见脚注**（重要前提不该藏在 hover 里）。
教训：**外链要放在它指代的东西旁边**；已写进 `ui-architecture.md` §7。

**诚实边界（第二次遇到，已放弃硬磕）**：本机 Chromium 的 CDP 通道不稳——`open` 能成功，
